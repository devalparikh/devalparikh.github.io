5:T7ec,<p>A lock to protect a resource accessed by distributed machines</p>
<h1 id="approaches">Approaches</h1>
<h3 id="single-lock-service-">Single lock service ❌</h3>
<ul>
<li>Single point of failure</li>
</ul>
<h3 id="lock-db-with-async-replication-">Lock DB with async replication ❌</h3>
<ul>
<li>Eventual consistency leading to multiple clients with lock at the same time</li>
</ul>
<h3 id="lock-db-with-sync-replication-">Lock DB with sync replication ❌</h3>
<ul>
<li>Not fault tolerant</li>
<li>If leader needs to replicate to all followers, if 1 follower is down, can't proceed</li>
</ul>
<h3 id="lock-db-with-quorum-consensus-using-fencing-token-">Lock DB with Quorum Consensus using Fencing Token ❌</h3>
<ul>
<li>A little more fault tolerant but not linearizable (not in order)</li>
<li>Might update 1 replicate, and other replicate is down (need Two Phase Commit (2pc) to fix that)</li>
<li>Quorum Consensus helps with fault tolerance but is not linearizable</li>
<li>Quorum Consensus is not linearizable since</li>
<li>What if some client finds a max Fencing Token (from > n/2 replicas) and needs to update, but the client fails to update because it went down
<ul>
<li>Then another client can read from > n/2 outdated replicas</li>
</ul>
</li>
</ul>
<h3 id="lock-db-with-distributed-consensus-using-fencing-token-">Lock DB with Distributed Consensus using Fencing Token ✅</h3>
<ul>
<li>Fault tolerant and linearizable</li>
<li>Distributed Consensus majority must accept (Two Phase Commit (2pc))</li>
<li>Example: RAFT</li>
<li>If leader fails, a up to date follower will be elected to leader (max Fencing Key)</li>
<li>Use this to guarantee who has the Lock with:
<ul>
<li>Fault Tolerance</li>
<li>Fencing Key used if somehow two clients have the Lock
<ul>
<li>two clients can get the Lock accidentally if a client has some process pause (ex: Garbage Collector) and hits TTL of Lock service and Lock is released</li>
<li>In this case the Fencing Key can be used to break the tie</li>
</ul>
</li>
</ul>
</li>
