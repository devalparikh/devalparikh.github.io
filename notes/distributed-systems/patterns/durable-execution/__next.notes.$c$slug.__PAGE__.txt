5:Tdbd,<p>A workflow (e.g. order checkout) is done in a <a href="/notes/distributed-systems/non-functional-attributes/durable/">durable</a> fashion (fulfills even if servers go down)</p>
<p>essentially a <a href="/notes/distributed-systems/patterns/durable-message-queue/">durable message queue</a> / job orchestrator with cached results
(so you can tie multiple steps together and can replay steps upon workflow retry)</p>
<p>opensource framework: temporal</p>
<p><strong>workflow</strong>: a function be to ran durably
<strong>activity</strong>: a workflow step with external dependency
<strong>node</strong>: server that runs the workflow and activities</p>
<p><strong>checkpoint</strong>: last tracked successful state
(note: it's not actually restarting from checkpoint, rather it restarts from scratch but uses cached activity results instead of re-running the already done activity)</p>
<h2 id="features">features</h2>
<ul>
<li>at-least-once execution
<ul>
<li>the workflow will restart if incomplete until the entire workflow is completed</li>
</ul>
</li>
<li>resuming
<ul>
<li>resume from checkpoint</li>
<li>this is important for
<ul>
<li>non-deterministic activity
<ul>
<li>(example: claude code workflow, call LLM activity, imagine node crashes and restarts session and new LLM responses were in the chat - bad experience)</li>
</ul>
</li>
<li>async / long wait activity (human input)</li>
</ul>
</li>
</ul>
</li>
<li>abstraction
<ul>
<li>abstract away the distributed systems complexities of durability for any function</li>
</ul>
</li>
</ul>
<h2 id="limitation">limitation</h2>
<ul>
<li>lacking at-most-once (exactly once) execution
<ul>
<li>more complex</li>
<li>restarting from checkpoint means the activity could have ran but node crashed before tracking activity finished, thus activity re-runs</li>
<li>compensate by making activities idempotent</li>
</ul>
</li>
<li>it is not for <a href="/notes/distributed-systems/databases/atomic/">Atomic</a> / transactional
<ul>
<li>you can pair durable execution with <a href="/notes/distributed-systems/patterns/saga/">SAGA</a> or <a href="/notes/distributed-systems/patterns/outbox/">outbox</a> to handle distributed transaction (if credit card step passes, but shipping fails ?)</li>
</ul>
</li>
</ul>
<h2 id="retrying-workflows">retrying workflows</h2>
<p>when: upon failure detection</p>
<ul>
<li>timeout, heart beat, etc
what:</li>
<li>retries from start but "skip" to last tracked step
how:</li>
<li>log when an activity starts</li>
<li>log when an activity ends</li>
<li>cache the result of the activity that ran</li>
<li>so retry actually just replays</li>
</ul>
<h2 id="durable-execution-vs-durable-message-queue">durable execution vs <a href="/notes/distributed-systems/patterns/durable-message-queue/">durable message queue</a></h2>
<p>job orchestrator like a processing/handling a message from a <a href="/notes/distributed-systems/events/message-queue/">Message Queue</a> and running the job, would re-run the entire job <strong>from the start</strong> upon a node failure</p>
<p>whereas, durable executor is more granular - it would resume from last tracked successful state</p>
<p>so sub steps (activities) like</p>
<ul>
<li>human approval or input
<ul>
<li><strong>durable execution can simply replay from cache</strong>
(instead of redoing or re-waiting)</li>
</ul>
</li>
<li>non-deterministic call like LLM
<ul>
<li><strong>durable execution can simply replay from cache</strong>
(instead of retry leading to another value)</li>
</ul>
</li>
