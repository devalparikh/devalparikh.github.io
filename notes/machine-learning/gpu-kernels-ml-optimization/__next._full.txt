11:T40e2,<h2 id="overview">Overview</h2>
<p>Understanding how to optimize ML/AI training at the GPU kernel level through custom CUDA programming, quantization techniques, and hardware-specific optimizations. This knowledge is critical for building high-performance ML infrastructure and understanding the lowest levels of neural network training optimization.</p>
<p><strong>Inspiration</strong>: Cursor's blog post about achieving 3.5x speedup in Mixture-of-Experts (MoE) layer performance through custom MXFP8 kernels on Blackwell GPUs, demonstrating that custom kernel development can unlock massive performance gains beyond what standard libraries provide.</p>
<h2 id="motivation">Motivation</h2>
<ul>
<li>Understand how ML/AI infrastructure works at the GPU kernel level, not just high-level frameworks</li>
<li>Learn custom kernel development for performance optimization (moving beyond PyTorch/TensorFlow abstractions)</li>
<li>Comprehend quantization techniques (MXFP8, FP8, BF16) for efficient training at scale</li>
<li>Understand modern GPU architectures (Hopper, Blackwell) and their implications for ML workloads</li>
<li>Gain ability to identify and fix performance bottlenecks in ML training pipelines</li>
<li><strong>Real-world impact</strong>: Cursor achieved 1.5x end-to-end training improvements on Blackwell and 2x gains vs Hopper</li>
</ul>
<h2 id="key-concepts">Key Concepts</h2>
<h3 id="1-gpu-architecture-fundamentals">1. GPU Architecture Fundamentals</h3>
<p><strong>Hardware Components</strong>:</p>
<ul>
<li><strong>Tensor cores</strong>: Specialized hardware for matrix multiplication operations</li>
<li><strong>Shared memory</strong>: Fast on-chip memory shared within a threadblock</li>
<li><strong>Register hierarchies</strong>: L1/L2 cache, registers, and memory bandwidth considerations</li>
<li><strong>Streaming Multiprocessors (SMs)</strong>: Basic execution units on GPU</li>
</ul>
<p><strong>Architecture Evolution</strong>:</p>
<ul>
<li><strong>Hopper architecture</strong>: Register-based accumulation for tensor operations</li>
<li><strong>Blackwell architecture</strong>: Introduces Tensor Memory (TMEM) - new on-chip storage
<ul>
<li>TMEM requires asynchronous data movement to registers</li>
<li>Creates pipeline bubbles where dequantization can take 1.76x the time of matrix multiplication</li>
<li>Requires different optimization strategies than Hopper</li>
</ul>
</li>
</ul>
<p><strong>Key Challenge</strong>: "Quantization time can truly kill the performance gain" - up to 76% of theoretical speedup can be lost to poorly optimized quantization</p>
<h3 id="2-cuda-programming--kernel-optimization">2. CUDA Programming &#x26; Kernel Optimization</h3>
<p><strong>Low-Level Programming</strong>:</p>
<ul>
<li><strong>PTX instructions</strong>: Assembly-level GPU programming</li>
<li><strong>tcgen05.mma instruction</strong>: Hardware-managed block scaling for efficient quantization</li>
<li><strong>Warp specialization</strong>: Assigning specialized warpgroups to different pipeline stages</li>
<li><strong>Memory synchronization</strong>: Managing data flow between TMEM, registers, and global memory</li>
</ul>
<p><strong>Optimization Patterns</strong>:</p>
<ul>
<li><strong>2-CTA matrix multiplication mode</strong>: 15-20% speedups through collaborative SM execution</li>
<li><strong>Persistent grid pattern</strong>: Scheduling one threadblock per SM for continuous operation</li>
<li><strong>Expert-wise supergrouping</strong>: L2 cache optimization strategies for grouped matrix operations</li>
<li><strong>Pipeline design</strong>: Overlapping computation and memory transfer to hide latency</li>
</ul>
<h3 id="3-low-precision-training--quantization">3. Low-Precision Training &#x26; Quantization</h3>
<p><strong>MXFP8 Format (Microscaled Floating-Point)</strong>:</p>
<ul>
<li>Uses FP8E4M3 elements (8-bit floating point: 1 sign, 4 exponent, 3 mantissa bits)</li>
<li><strong>32-block scaling</strong>: Scale factors applied per 32-element blocks</li>
<li>Maintains training quality comparable to BF16 (nearly indistinguishable loss curves)</li>
<li>Reduces memory bandwidth requirements significantly</li>
</ul>
<p><strong>Precision Formats Comparison</strong>:</p>
<ul>
<li><strong>BF16</strong> (Brain Float 16): Standard high-precision training format</li>
<li><strong>FP8</strong>: 8-bit floating point (E4M3 or E5M2 variants)</li>
<li><strong>MXFP8</strong>: Block-scaled FP8 with per-block scale factors</li>
<li><strong>INT8</strong>: Integer quantization (typically for inference)</li>
</ul>
<p><strong>Trade-offs</strong>:</p>
<ul>
<li><strong>Precision vs Memory Bandwidth</strong>: Lower precision = less data movement</li>
<li><strong>Precision vs Training Quality</strong>: Must maintain convergence properties</li>
<li><strong>Quantization Overhead</strong>: Time spent quantizing/dequantizing must be less than bandwidth savings</li>
</ul>
<p><strong>Quantization Optimization Example</strong>:</p>
<ul>
<li>Cursor achieved 6.2+ TB/s bandwidth utilization (vs 4.5 TB/s from TransformerEngine/TorchAO)</li>
<li>Key: Producing scale factors in exact layout expected by tensor core instructions</li>
<li>Eliminates costly reshape operations that can dominate runtime</li>
</ul>
<h3 id="4-matrix-multiplication-optimization-for-moe">4. Matrix Multiplication Optimization for MoE</h3>
<p><strong>Grouped Matrix Multiplication Variants</strong>:</p>
<ul>
<li><strong>Fprop</strong> (Forward propagation): Input × Weights</li>
<li><strong>Dgrad</strong> (Data gradient): Error × Weights^T</li>
<li><strong>Wgrad</strong> (Weight gradient): Input^T × Error</li>
</ul>
<p><strong>Block-Scaling Concepts</strong>:</p>
<ul>
<li>Per-block vs per-tensor scaling strategies</li>
<li>Hardware-managed scaling with tensor cores</li>
<li>Impact on accumulation precision</li>
</ul>
<p><strong>Performance Bottlenecks</strong>:</p>
<ul>
<li>Quantization overhead can dominate if not optimized</li>
<li>Memory bandwidth saturation limits</li>
<li>Pipeline bubbles from synchronization</li>
<li>Cache coherency in grouped operations</li>
</ul>

<h3 id="5-performance-analysis--profiling">5. Performance Analysis &#x26; Profiling</h3>
<p><strong>Metrics to Track</strong>:</p>
<ul>
<li><strong>Memory bandwidth utilization</strong>: TB/s achieved vs theoretical maximum</li>
<li><strong>Occupancy</strong>: Percentage of GPU resources actively used</li>
<li><strong>Pipeline efficiency</strong>: Ratio of compute time to synchronization/transfer time</li>
<li><strong>Quantization overhead</strong>: Time spent in quantize/dequantize operations</li>
<li><strong>Speedup metrics</strong>: End-to-end training throughput (tokens/sec/GPU)</li>
</ul>
<p><strong>Analysis Techniques</strong>:</p>
<ul>
<li>GPU profiling tools (NVIDIA Nsight, nvprof)</li>
<li>Understanding SM utilization patterns</li>
<li>Identifying memory-bound vs compute-bound operations</li>
<li>Bottleneck analysis (where is time actually spent?)</li>
</ul>

<h2 id="notes">Notes</h2>
<h3 id="initial-insights">Initial Insights</h3>
<ul>
<li><strong>The 76% rule</strong>: Poorly optimized quantization can consume 76% of theoretical speedup gains</li>
<li><strong>Layout matters</strong>: Producing data in the exact layout tensor cores expect eliminates costly reshapes</li>
<li><strong>Architecture-specific</strong>: What works on Hopper may need complete redesign for Blackwell (TMEM changes everything)</li>
<li><strong>Beyond libraries</strong>: Even mature libraries (TransformerEngine) left 37% performance on the table (4.5 vs 6.2 TB/s)</li>
</ul>
<h3 id="why-this-matters">Why This Matters</h3>
<p>As models scale to trillions of parameters and training costs soar, kernel-level optimization becomes economically critical. A 2x training speedup means:</p>
<ul>
<li>Half the GPU-hours for same results</li>
<li>Half the energy consumption</li>
<li>Half the time to experiment and iterate</li>
<li>Massive cost savings at scale</li>
</ul>
<p>Understanding this level allows you to:</p>
<ul>
<li>Build infrastructure that doesn't hit scaling walls</li>
<li>Identify when hardware upgrades vs software optimization makes sense</li>
<li>Contribute to or build ML frameworks rather than just use them</li>
</ul>
