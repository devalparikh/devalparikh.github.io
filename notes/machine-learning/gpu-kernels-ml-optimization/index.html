GPU Kernels for ML/AI Infrastructure - Custom Optimization and Quantization

Updated Oct 31, 2025

#ml-infrastructure#gpu-optimization#cuda#quantization#performance#low-precision-training#tensor-cores

Overview

Understanding how to optimize ML/AI training at the GPU kernel level through custom CUDA programming, quantization techniques, and hardware-specific optimizations. This knowledge is critical for building high-performance ML infrastructure and understanding the lowest levels of neural network training optimization.

Inspiration: Cursor's blog post about achieving 3.5x speedup in Mixture-of-Experts (MoE) layer performance through custom MXFP8 kernels on Blackwell GPUs, demonstrating that custom kernel development can unlock massive performance gains beyond what standard libraries provide.

Motivation

  • Understand how ML/AI infrastructure works at the GPU kernel level, not just high-level frameworks
  • Learn custom kernel development for performance optimization (moving beyond PyTorch/TensorFlow abstractions)
  • Comprehend quantization techniques (MXFP8, FP8, BF16) for efficient training at scale
  • Understand modern GPU architectures (Hopper, Blackwell) and their implications for ML workloads
  • Gain ability to identify and fix performance bottlenecks in ML training pipelines
  • Real-world impact: Cursor achieved 1.5x end-to-end training improvements on Blackwell and 2x gains vs Hopper

Key Concepts

1. GPU Architecture Fundamentals

Hardware Components:

  • Tensor cores: Specialized hardware for matrix multiplication operations
  • Shared memory: Fast on-chip memory shared within a threadblock
  • Register hierarchies: L1/L2 cache, registers, and memory bandwidth considerations
  • Streaming Multiprocessors (SMs): Basic execution units on GPU

Architecture Evolution:

  • Hopper architecture: Register-based accumulation for tensor operations
  • Blackwell architecture: Introduces Tensor Memory (TMEM) - new on-chip storage
    • TMEM requires asynchronous data movement to registers
    • Creates pipeline bubbles where dequantization can take 1.76x the time of matrix multiplication
    • Requires different optimization strategies than Hopper

Key Challenge: "Quantization time can truly kill the performance gain" - up to 76% of theoretical speedup can be lost to poorly optimized quantization

2. CUDA Programming & Kernel Optimization

Low-Level Programming:

  • PTX instructions: Assembly-level GPU programming
  • tcgen05.mma instruction: Hardware-managed block scaling for efficient quantization
  • Warp specialization: Assigning specialized warpgroups to different pipeline stages
  • Memory synchronization: Managing data flow between TMEM, registers, and global memory

Optimization Patterns:

  • 2-CTA matrix multiplication mode: 15-20% speedups through collaborative SM execution
  • Persistent grid pattern: Scheduling one threadblock per SM for continuous operation
  • Expert-wise supergrouping: L2 cache optimization strategies for grouped matrix operations
  • Pipeline design: Overlapping computation and memory transfer to hide latency

3. Low-Precision Training & Quantization

MXFP8 Format (Microscaled Floating-Point):

  • Uses FP8E4M3 elements (8-bit floating point: 1 sign, 4 exponent, 3 mantissa bits)
  • 32-block scaling: Scale factors applied per 32-element blocks
  • Maintains training quality comparable to BF16 (nearly indistinguishable loss curves)
  • Reduces memory bandwidth requirements significantly

Precision Formats Comparison:

  • BF16 (Brain Float 16): Standard high-precision training format
  • FP8: 8-bit floating point (E4M3 or E5M2 variants)
  • MXFP8: Block-scaled FP8 with per-block scale factors
  • INT8: Integer quantization (typically for inference)

Trade-offs:

  • Precision vs Memory Bandwidth: Lower precision = less data movement
  • Precision vs Training Quality: Must maintain convergence properties
  • Quantization Overhead: Time spent quantizing/dequantizing must be less than bandwidth savings

Quantization Optimization Example:

  • Cursor achieved 6.2+ TB/s bandwidth utilization (vs 4.5 TB/s from TransformerEngine/TorchAO)
  • Key: Producing scale factors in exact layout expected by tensor core instructions
  • Eliminates costly reshape operations that can dominate runtime

4. Matrix Multiplication Optimization for MoE

Grouped Matrix Multiplication Variants:

  • Fprop (Forward propagation): Input × Weights
  • Dgrad (Data gradient): Error × Weights^T
  • Wgrad (Weight gradient): Input^T × Error

Block-Scaling Concepts:

  • Per-block vs per-tensor scaling strategies
  • Hardware-managed scaling with tensor cores
  • Impact on accumulation precision

Performance Bottlenecks:

  • Quantization overhead can dominate if not optimized
  • Memory bandwidth saturation limits
  • Pipeline bubbles from synchronization
  • Cache coherency in grouped operations

Benchmark Results (Cursor's Implementation):

Operation Hopper BF16 Blackwell BF16 Blackwell MXFP8 Speedup
MoE Forward 32.36 ms 25.96 ms 9.45 ms 3.4x
MoE Backward 63.24 ms 59.17 ms 17.04 ms 3.7x
End-to-end 12k TPS/GPU 16k TPS/GPU 24k TPS/GPU 2x

5. Performance Analysis & Profiling

Metrics to Track:

  • Memory bandwidth utilization: TB/s achieved vs theoretical maximum
  • Occupancy: Percentage of GPU resources actively used
  • Pipeline efficiency: Ratio of compute time to synchronization/transfer time
  • Quantization overhead: Time spent in quantize/dequantize operations
  • Speedup metrics: End-to-end training throughput (tokens/sec/GPU)

Analysis Techniques:

  • GPU profiling tools (NVIDIA Nsight, nvprof)
  • Understanding SM utilization patterns
  • Identifying memory-bound vs compute-bound operations
  • Bottleneck analysis (where is time actually spent?)

Prerequisites

Before diving into this topic, ensure understanding of:

  • Neural networks: Basic architecture, forward/backward propagation, gradient descent
  • GPU computing concepts: Parallelism, memory hierarchies, SIMD execution
  • Programming experience: Python (for ML frameworks), C/C++ (for CUDA)
  • Linear algebra: Matrix operations, dimensions, reduction operations
  • Computer architecture: Memory hierarchies, caching, bandwidth concepts

Nice to have:

  • Experience with PyTorch or TensorFlow
  • Basic CUDA programming exposure
  • Understanding of floating-point representations
  • Familiarity with compilation and optimization

Learning Path

Phase 1: GPU Computing Foundations (10-15 hours)

  1. CUDA programming basics (threads, blocks, grids)
  2. Memory hierarchy (global, shared, registers)
  3. Basic kernel writing and optimization
  4. Profiling tools introduction

Phase 2: GPU Architecture Deep Dive (8-12 hours)

  1. Tensor core architecture and capabilities
  2. Hopper architecture specifics
  3. Blackwell architecture and TMEM
  4. Warp-level programming concepts

Phase 3: Quantization & Low-Precision Training (10-15 hours)

  1. Floating-point representations (FP32, BF16, FP8)
  2. MXFP8 and block-scaling concepts
  3. Quantization-aware training techniques
  4. Trade-offs analysis (precision vs performance)

Phase 4: Advanced Kernel Optimization (12-18 hours)

  1. PTX assembly programming basics
  2. Warp specialization patterns
  3. Pipeline design and optimization
  4. Memory access pattern optimization
  5. Case study: Reproducing simplified MoE optimization

Notes

Initial Insights

  • The 76% rule: Poorly optimized quantization can consume 76% of theoretical speedup gains
  • Layout matters: Producing data in the exact layout tensor cores expect eliminates costly reshapes
  • Architecture-specific: What works on Hopper may need complete redesign for Blackwell (TMEM changes everything)
  • Beyond libraries: Even mature libraries (TransformerEngine) left 37% performance on the table (4.5 vs 6.2 TB/s)

Why This Matters

As models scale to trillions of parameters and training costs soar, kernel-level optimization becomes economically critical. A 2x training speedup means:

  • Half the GPU-hours for same results
  • Half the energy consumption
  • Half the time to experiment and iterate
  • Massive cost savings at scale

Understanding this level allows you to:

  • Build infrastructure that doesn't hit scaling walls
  • Identify when hardware upgrades vs software optimization makes sense
  • Contribute to or build ML frameworks rather than just use them
