<h1 id="chapter-1-clean-code">Chapter 1: Clean code</h1>
<ul>
<li>we will always have code</li>
<li>specifying requirements is programming</li>
<li>the specification is code</li>
<li>sure there will be abstractions, but we will always need code</li>
<li>Bad code
<ul>
<li>wading - slowed down by bad code</li>
<li>ambiguity of purpose</li>
<li>muddled intent</li>
<li>room for speculation</li>
</ul>
</li>
<li>Clean code
<ul>
<li>focused</li>
<li>crisp on writers intent</li>
<li>easy for other ppl to enhance it</li>
<li>no <strong>duplication</strong></li>
<li>method - says what it does
<ul>
<li>impl - says how it is done
<ul>
<li>wrap particular implementation in a more abstract method or class</li>
</ul>
</li>
</ul>
</li>
</ul>
</li>
<li>total cost of owning a mess
<ul>
<li>asymptotically lowers productivity</li>
<li>each change requires untangling and understanding</li>
</ul>
</li>
<li>a broken window in an apt causes other ppl to not care and make a mess</li>
<li>doing 1 thing
<ul>
<li>object or a method should just focus on 1 thing</li>
</ul>
</li>
<li>Ron Jeffries
<ul>
<li>no duplication</li>
<li>one thing</li>
<li>expressiveness</li>
<li>tiny abstractions</li>
</ul>
</li>
<li>we read old code 10x more than writing during writing. so we want old code to be easy to read -> easy to read = easy to write</li>
</ul>
<h1 id="chapter-2-meaningful-names">Chapter 2: Meaningful Names</h1>
<ul>
<li>intention-revealing names</li>
