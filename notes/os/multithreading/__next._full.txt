11:T752,<p>on 1 CPU core -> <a href="/notes/os/concurrency/">concurrency</a> only (swapping between threads/tasks)
on N CPU cores -> <a href="/notes/os/concurrency/">concurrency</a> and <a href="/notes/os/parallelism/">parallelism</a></p>
<h1 id="models">models</h1>
<h2 id="thread-per-task">thread per task</h2>
<ul>
<li>lots of threads may sit blocked waiting on I/O, consuming unnecessary memory</li>
<li>still high <a href="/notes/os/concurrency/">concurrency</a> and cpu utilization (cpu does not get blocked by blocked thread), but when threads are blocked, new threads are spawned (keeping the blocked threads in memory)</li>
</ul>
<h2 id="async--event-loop">async / event loop</h2>
<ul>
<li>a small number of threads stop working on the blocked task while it waits and <strong>pick up other work</strong></li>
<li>re-allocate blocked threads to work on another task</li>
<li>ex: js event loop</li>
</ul>
<p>benefits:</p>
<ul>
<li>less memory per concurrent task</li>
<li>less thread/context-switch overhead</li>
<li>scales much better for <strong>I/O-heavy workloads</strong></li>
</ul>
<p>problem it solves:</p>
<ul>
<li>waiting threads (even if CPU is not processing them) take up memory</li>
<li>scaling many waiting threads uses <strong>unnecessary memory</strong> due to thread memory overhead</li>
<li>synchronous I/O by definition makes the thread wait for I/O response</li>
<li>to solve that, we can make asynchronous I/O calls</li>
<li>issue: asynchronous by itself means we fire and forget, lose track of the response</li>
<li>what if we need/want to response tracked</li>
<li>that's where event loops are helpful</li>
</ul>
<p>track the asynchronous threads to get response information without holding the thread blocked, causing many new threads to spawn to take on active work
